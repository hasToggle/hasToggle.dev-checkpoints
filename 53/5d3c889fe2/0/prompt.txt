<result>## Security Audit Report: `apps/web`

No Critical findings and nothing in the code blocks shipping outright. The one High — unthrottled confirmation mail from `/api/confirm` — needs a platform-level rate limit before launch. Every finding was checked against the code except the Sentry part of finding 3.

### Summary
- Critical: 0
- High: 1
- Medium: 1
- Low: 4

### Findings

#### 1. [HIGH] `/api/confirm` can send mail to arbitrary addresses with no durable rate limit
- **Location:** `/Users/eric/conductor/workspaces/hasToggle.dev/singapore/apps/web/app/api/confirm/route.ts:33-34,70-81,288` and `/Users/eric/conductor/workspaces/hasToggle.dev/singapore/apps/web/lib/rate-limit.ts`
- **Description:** Upstash is not configured in production, so both rate-limit windows live in each instance's memory.
  - The only controls that persist across instances are the 2-minute per-address cooldown (DB) and the once-a-day reminder idempotency key for confirmed addresses.
  - Nothing limits how many different addresses a caller can submit.
  - Even when the limiter works, one IP is allowed 10 sends per 10 minutes, about 1,440 mails a day.
  - There is no bot challenge and no global send ceiling.
  - `request.json()` ignores `Content-Type` and the route does not check `Origin`. A cross-site `text/plain` form POST is therefore accepted, which lets an attacker spread requests across visitors' IPs.
- **Exploit:** A script POSTs `{"email": &lt;victim N&gt;}` for a list of addresses, rotating IPs or simply landing on cold instances.
  - Each victim gets a branded confirmation mail, repeatable every 2 minutes (subscription bombing).
  - The same loop uses up the Resend quota and draws spam complaints against the sending domain.
  - Real signups then stop receiving confirmation mail, which takes the waitlist funnel down on launch day.
- **Recommendation (minimum acceptable):**
  1. Add a Vercel WAF rate-limit rule on `POST /api/confirm`, around 5 per 10 minutes per IP. This needs no code and is shared across instances.
  2. Make the per-address cap durable. Store `confirmationsSent` and a window start on the subscriber row, allow at most 3 per 24 hours, and replace the 2-minute cooldown with it.
  3. Reject requests unless `Content-Type` is `application/json` and `Origin` matches `confirmationOrigin`.

  Strongly advised on top of that: Vercel BotID or Turnstile on the form, and a global daily send circuit breaker. Upstash would replace (2) once it is configured.

#### 2. [MEDIUM] The confirmation link changes state on GET, so mail scanners can complete the double opt-in
- **Location:** `/Users/eric/conductor/workspaces/hasToggle.dev/singapore/apps/web/app/api/confirmed/route.ts:8-66`
- **Description:** Following the link sets `emailVerified` and creates the Resend contact. The unsubscribe route deliberately avoids acting on GET for this exact reason (its own comment, `api/unsubscribe/route.ts:10-14`), but the confirm route does not.
- **Exploit:** An attacker submits a victim's address at an organisation whose mail gateway pre-fetches links. The scanner "confirms" the signup, the victim joins the broadcast list without consenting, and the consent record is worthless.
- **Recommendation:** Follow the unsubscribe pattern. GET shows a page with a "Confirm" button, and POST performs the write.

#### 3. [LOW] Unsubscribe link secrets can reach third-party analytics and Sentry
- **Location:** `/Users/eric/conductor/workspaces/hasToggle.dev/singapore/apps/web/app/unsubscribe/page.tsx`, rendered under `app/layout.tsx:45` (`AnalyticsProvider`), and `packages/analytics/instrumentation-client.ts:30`
- **Description:** `/unsubscribe?id=…&amp;sig=…` records a PostHog, GA or Vercel Analytics pageview with the full URL. The `sig` never expires, and `id` is the subscriber's `_id`.
- **Impact:** Anyone who can read analytics data can unsubscribe that person.
- **Unverified:** Sentry request data on server errors probably captures query strings as well, including `token=` on `/api/confirmed`. `sendDefaultPii` is unset, which is good.
- **Recommendation:** Render `/unsubscribe` and `/confirmed` outside `AnalyticsProvider`, or strip the query string with PostHog `before_send` or `sanitize_properties`. Add a Sentry `beforeSend` that redacts `token`, `sig` and `id` from URLs.

#### 4. [LOW] A public server action clears the landing page cache for everyone
- **Location:** `/Users/eric/conductor/workspaces/hasToggle.dev/singapore/apps/web/app/[locale]/(playground)/shell/actions.ts:15-33`
- **Description:** `updateTag("landing-shell")` sits behind the same in-memory limiter. A loop spread across instances keeps the landing page rendering dynamically, which costs money and latency.

#### 5. [LOW] A log line can contain an email address
